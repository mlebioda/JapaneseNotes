# Orchestrator Agent Fixes

## Goal

The orchestrator.md agent has a collection of A2A wiring bugs, a broken revision loop, a missing post pipeline, incorrect reporting, and no explicit prohibition rules. A user constraint has also been added requiring the orchestrator to never modify files directly — it may only orchestrate via sub-agent calls. These fixes make the orchestrator reliable for all task types and enforce the intended read-only coordination role.

## Approach

All changes are confined to `.claude/agents/orchestrator.md`. Each fix is surgical: replace or add the affected block only. The tools list is unchanged (already lacks Edit/Write). The Hard rules section gains the write-prohibition entries. Stage-level prose is updated to resolve the synthetic TARGET bug, the slug-resolution gap, the revision loop protocol, the post pipeline, and the DONE block accuracy.

## Steps

1. **Verify tools list** — `.claude/agents/orchestrator.md` frontmatter. Confirm `Edit` and `Write` are absent (they already are). No change needed if absent; add an explicit comment in the Hard rules referencing why.

2. **Fix issue 1 + 2 — `new` task TARGET** — In Stage 1 prose (and Stage 2 planner call template), replace the synthetic `"related: <topic>"` notation. For `new` tasks the orchestrator must resolve a real existing file path before calling reviewer: find the closest related skill or agent file under `.cowork/skills/` or `.claude/agents/` using `ls`/`find` via Bash, then pass that absolute path as `TARGET`. Update the Stage 1 call template and the accompanying explanation text accordingly.

3. **Fix issue 3 — revision loop** — In Stage 2, replace the "Revise X" branch. Drop `REVISE: true` (not defined in planner's interface). Instead, re-call planner using the standard `REVIEWER_BRIEF: true` format, passing the original `TARGET`, the original `SUMMARY`, the original `ISSUES`, and appending a `REVISION_NOTES: <user feedback>` field so planner knows it is a revision run. Document this field addition in the plan note (it is an extension, not a breaking change to planner).

4. **Fix issue 4 — slug resolution** — After Stage 2 completes, orchestrator cannot know the slug planner chose. Add a post-Stage-2 step: run `ls -t Plans/*-plan.md | head -1` via Bash to find the newest plan file, then extract the slug from the filename. Store this as a working variable used in the Stage 3 implementer call template (`Plans/<slug>-plan.md`, `Plans/<slug>-tasks.md`). Document the Bash one-liner in the pipeline section.

5. **Fix issue 5 — post pipeline** — The `post` task type currently has no pipeline steps. Add a Stage for it: after classification as `post`, call scribe directly in `post` mode (this is the one permitted direct-scribe call from orchestrator). Template:
   ```
   subagent_type: scribe
   prompt:
   MODE: post
   TOPIC: <user's topic>
   ```
   Then present the generated post to the user.

6. **Fix issue 6 — DONE block scribe attribution** — Replace the hardcoded `"captured by skill-implementer"` line. Use conditional language that reflects the actual session: for `change`/`new` tasks note "captured by skill-implementer (per-file) + reviewer (stage 4 if run)"; for `review-only` note "captured by reviewer"; for `post` note "post generated by scribe".

7. **Fix issue 7 — Hard rules: explicit prohibitions** — Add to the Hard rules section:
   - Never use Edit or Write tools — the orchestrator has no write access; all file changes go through skill-implementer.
   - Never call skill-implementer without a plan file having been created by planner in the current session.
   - Never call scribe directly except in the `post` pipeline or the `review-only` end-of-session path.
   - Never skip a pipeline stage on own initiative; present findings and wait for user confirmation at every gate.
   - Exception: orchestrator may write to `.cowork/tmp/orchestrator-handoff.md` if a stage-to-stage data handoff requires a temp file (e.g., passing slug or reviewer output between agent calls).

8. **Fix issue 8 — DONE block stage 4 scribe** — Add "Stage 4 reviewer capture" to the Stages completed list in the DONE block template, conditional on whether the user ran stage 4.

## Risks

- Changing the Stage 1 TARGET resolution for `new` tasks requires orchestrator to do a Bash lookup before calling reviewer. If `.cowork/skills/` is empty or the topic has no close match, the orchestrator must fall back gracefully (pick the most structurally similar file, e.g. another agent file).
- The `REVISION_NOTES` field added to the planner call in Step 3 is not defined in planner's current A2A interface. Planner will receive it as unknown content; it should handle it gracefully (planner reads briefs as free text). Low risk, but the planner's A2A section could be updated in a follow-up to formally recognise this field.
- The slug-resolution Bash one-liner (Step 4) depends on filesystem mtime ordering. On iCloud-synced vaults, mtime may lag. A more robust fallback is to parse the newest file matching `Plans/*-plan.md` by creation order. Document this caveat in the pipeline.
- No plugin export data (`<!--ID:-->`, `TARGET DECK`, `# Summary`) is touched — this file is an agent definition with no Anki integration.
